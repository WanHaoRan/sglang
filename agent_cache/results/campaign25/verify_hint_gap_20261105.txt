Read-only check, 2026-11-05: does the 128-user gap between the hint-free arm (campaign 25) and the hinted arms measure what hints buy?
Four independent checks, one lens each, in the order they finished. Scripts as run: frozen/oracle_scripts_staging/c25_c128/verify_20261105/
(some read pickles they wrote under /tmp, not kept). Key code lines and counts were re-checked by hand before the docs were corrected.

== engine paths: verdict claim_partly_holds
Not cleanly. In engine_5df71c4bf0_v2 the hint-free arm is missing more than the hint's information: it also lacks three mechanisms that live inside the next-turn prefetcher but run only on queue and cache state, and the hint-free losses in the logs go through exactly those gaps. First, only the prefetcher sets read deadlines. Without it every read is 'now', and 'now' reads skip the 512-page window and the 813,824-token budget, so the hint-free arm's deadline order does nothing: 4,476 of 4,476 reads were 'now', with a median of 8,702 pages in flight at dispatch against 603 in the oracle. Second, poll interval 0 turns off paced retries in both arms, and only the prefetcher's queued-turn refetch replaces them. In the hint-free first 2 h, 512 turns lost their read to host_capacity and 526 more were refused by the rate limiter; none was retried, and each recomputed about 18-20K tokens. The oracle re-read history found missing while a turn was queued 312 times, before the turn reached the head. Third, next_use protects a queued turn's tail from the moment it arrives, which is queue state; LRU evicts those paths (3,662 shrink events against 5). Some parts genuinely need the hint: 4,941 of the oracle's 5,400 reads were staged before the turn arrived, and sessions that ended or return far ahead are evicted first. So the hint may well matter, but this comparison cannot say how much.

- Q1: device prefix shrinks before admission (same code in both arms, no hint involved)
  evidence: scheduler.py:4017-4021 calls _prefetch_after_device_hit_loss (3232-3258). It only runs for queued requests the admission loop reaches with their read finished (3999-4005). It compares device+host match (len(prefix_indices)+host_hit_length) with storage_prefetch_last_match_len (set at 3149-3150). Below the 8-attempt cap it calls _retry_storage_prefetch (3211-3230) -> _prefetch_kvcache -> prefetch_from_storage (3169-3179). Under wait_complete the turn then waits for that read (unified_radix_cache.py:2238-2241). Deadline of the re-read: None in the hint-free arm; in the oracle, queue position, or None at position <=1. Logs, first 2 h, pattern 'device prefix shrank before admission': hint-free 3,667 lines / 3,662 rids (about 37 % of returning turns), mean shrink 18,224 tokens. What followed: 2,980 re-reads launched, 523 revoked for host_capacity, 164 with no read (161 refused by the rate limiter). Oracle: 5 lines. The 2,971 hint-free turns that re-read at the head waited 85.3 s on average in the queue, against 12.3 s for unaffected turns (ReqTimeStats queue_duration).
  needs hints: no
  could explain the gap: none by itself (identical code); it is the channel through which the differences below act
- Q2a: a read revoked for host capacity is never retried in either arm by the cache itself
  evidence: unified_radix_cache.py:2959-2993. _launch_storage_hit does alloc -> evict_host -> falls back to a shorter prefix of at least 256 tokens. If that fails: _finish_storage_prefetch(reason='host_capacity'), which only does accounting (2626-2644); then revoke_pending_prefetch (2874-2907: un-parks, pops ongoing_prefetch, releases the anchor host lock); then poll_miss (2987-2989). storage_prefetch.py:64-67 cancels non-immediate retries when the interval is 0. With no ongoing prefetch, check_prefetch_progress returns True (unified_radix_cache.py:2326-2327), so the turn is admitted and recomputes. The only immediate retry (refetch, 2661-2666) is called only on the buffer-mode anchor-loss path (2937). Logs: hint-free srs_dispatch launched=0 = 535 in the first 2 h (535 rids); 513 were admitted with no further prefetch_start. ReqTimeStats: 512 turns whose last read was revoked recomputed a mean 19,801 tokens (input_len - cached_input_len). Oracle: launched=0 = 0.
  needs hints: no: any retry (poll interval > 0, or a queue-state refetch) uses no hint
  could explain the gap: large: 512 turns x ~19.8K recomputed tokens
- Q2b: rate-limiter refusals, a second loss path of the same size that the stated mechanism leaves out
  evidence: prefetch_from_storage (unified_radix_cache.py:2121-2125) checks prefetch_rate_limited (cache_controller.py:1239-1244: in-flight + pinned >= 0.5 x host pool = 813,824 tokens); if limited it calls poll_miss, which is dropped at interval 0. Every submitted lookup logs s2h_query (cache_controller.py:1302; hybrid_cache_controller.py:841), so a lookup that never reached the storage query shows as prefetch_start (tokens >= 256) with no s2h_query for the same rid. Hint-free: 641 such lookups (378 at arrival, 161 shrink re-queries, 96 read later, 6 never admitted). All 641 fell at estimated occupancy >= 813,824 (my estimate from srs_dispatch, pin and success lines). 526 admitted turns had no read at all and recomputed a mean 18,159 tokens. Oracle: estimated occupancy peaked at 557K, so 0 refusals; its 4,407 lookups without an s2h_query are arrivals joining a staged read already in flight (2071-2075). Scripts: /tmp/claude-1001/-home-wanhr-sglang/7c93b1d5-dc1c-431d-8d3e-efb4ae23a30d/scratchpad/verify/scan_declines.py and scan_ratelimit.py
  needs hints: no
  could explain the gap: large: about as many turns as the host_capacity path
- Q4: without hints every read is due now, and 'now' reads bypass the window and budget, so the hint-free arm's deadline order does nothing
  evidence: read_deadline_fn is set only by the prefetcher (next_turn_prefetch.py:194-195); otherwise _read_deadline returns None (unified_radix_cache.py:3049-3051). StorageReadScheduler.dispatch sends None deadlines first and applies the 512-page window and the 813,824-token budget only to timed reads (storage_read_scheduler.py:105-122). Host room is charged at dispatch, sized to the allocation (unified_radix_cache.py:3021-3025); a parked read holds nothing (2786-2787). Pinned spans count against the limiter through extra_occupancy_fn (577). Logs, srs_park deadline_ms: hint-free 4,476 of 4,476 'now'; oracle 5,339 of 5,400 timed. srs_dispatch inflight_pages: hint-free median 8,702, p90 12,687, max 15,342 pages; oracle 603 / 896 / 1,695. Pins do work in both arms (srs_pin 3,938 vs 5,324).
  needs hints: partly: for a queued turn the oracle's deadline is now + (position+0.5)/admission rate (next_turn_prefetch.py:727-731; next_turn_estimators.py:101-106), queue state only. Only reads before arrival use the hinted arrival (721-726).
  could explain the gap: large: unpaced reads are what push in-flight + pinned past the limiter and the host pool
- Q2c: the next-turn prefetcher's queued-turn refetch (case 2) is a rescue path that uses no hint information
  evidence: tick (next_turn_prefetch.py:311-358) -> _check_queued (458-518) -> _wants_refetch (520-564); in the scheduler, _process_next_turn_prefetch/_on_next_turn_refetch (scheduler.py:3194-3209), run every pass after the retry pass (3655-3656). It does not use up the 8-attempt budget (3201-3203). Inputs: that a plan exists, plan.key, queue position and admission rate, a read-only residency probe (resident_prefix_len, unified_tree_core.py:931-965), any ongoing prefetch, and the rate limiter. In deadline mode the trigger-time gates are skipped (480, 493); it never reads next_gap_s or session end. hicache_hook.py:242-249 forces poll interval 0 with the prefetcher on because this refetch replaces paced retries. The hint-free arm sets poll interval 0 itself (start_server.sh:163-164, same in the campaign25 archive) with nothing replacing them. Logs: oracle ntp_refetch issued=1: 312 in 2 h (none with issued=0), median 2.0 s after arrival, median 15,168 missing tokens. 284 were for turns with no staged or earlier read, i.e. history found missing while queued.
  needs hints: no in information; it is gated on a plan only because plans are keyed by the hinted next_rid. The request's own tokens could serve as the key.
  could explain the gap: large: it covers all three hint-free loss paths (eviction while queued, host_capacity, rate limiter) before the turn reaches the head
- Q3: how next_use ranks nodes a queued turn matched, and what LRU allows
  evidence: Priorities (next_use_eviction.py:82-93): ENDED 0 < OVERDUE 1 < FAR 2 < UNKNOWN (LRU) 3 < SOON 4. Both device eviction (full.py:194-228) and host eviction (full.py:234-261) use them. At commit (next_turn_prefetch.py:265-288): next_use = hinted arrival + wait; no hint means ended. At arrival (439-445): the session tail gets next_use = now. Log: 15,652 of 31,792 nue_register lines are arrival registrations; 447 ended; 107 more than 300 s ahead. So protection of a queued turn comes from the arrival event; the hint only maps session -> tail node, and req.last_node from the arrival match could do the same. Caveat: a turn queued more than 60 s drops to OVERDUE (88-90) and is evicted before LRU nodes. Oracle queue_duration max was 50.6 s (none over 60 s); the hint-free arm had 3,641 turns over 60 s, so the code as written would not protect hint-free-length waits. LRU: lock_ref is taken only at admission (schedule_policy.py:1466-1473 -> 1003-1005); init_next_round_input only matches (schedule_batch.py:1624). A queued turn holds only the read anchor's host lock (unified_radix_cache.py:2131-2136; only the anchor, full.py:271-279) and a landed-span pin released at admission (3091-3121, 3641-3642). The match stamps last_access_time (unified_tree_core.py:983-987) at arrival, and again only when the admission loop reaches the turn (scheduler.py:4017), so turns deep in the queue age. The oracle evicted more, not less: host 110.7M vs 98.1M tokens, device 248.7M vs 147.8M in 2 h, while serving 16,140 vs 10,333 requests. The difference is which nodes go.
  needs hints: partly: protecting queued turns needs only queue state; choosing among non-queued victims (ended first, far first, by predicted return) needs session end and gap
  could explain the gap: large: 3,662 vs 5 shrink events
- Mechanisms that do need the hint
  evidence: Pre-arrival staging: _check_pending_deadline (next_turn_prefetch.py:671-713) and _stage (782-819) use next_rid and the predicted arrival from next_gap_s; the deadline for such a read is 721-726. In the oracle 4,941 of 5,400 parked reads were pre-arrival, parked 26-66 s (deciles) ahead of predicted admission; only 398 were reads for queued turns (86 own lookups timed, 61 'now', 312 refetches). Commit-time next_use (265-288) and _end_session/_expire (745-756, 821-835) also use hint content.
  needs hints: yes
  could explain the gap: unknown: these carry most of the oracle's reads, so they may matter a lot, but no run removes them alone

open questions:
- No run isolates hint information. The cleanest test is a hint-free engine at x10 / 128 users with queue-position deadlines, refetch for queued turns using their own tokens, and arrival-time protection. A cheaper partial test is three_tier_wc_dl with poll interval 8: the only existing run, 20261011_191741_three_tier_wc_dl_NAT160, is at x70 tool gaps.
- Would pacing by queue position alone avoid the rate-limiter and host_capacity losses when every read starts after arrival? The oracle staged 91.5 % of its reads before arrival, so its pacing was mostly hint-dated.
- My first-2 h counts differ from the brief's: 535 launched=0 against its 550, and about 1,038 turns recomputing 18-20K tokens (512 host_capacity + 526 rate-limiter) against its 610. The definitions and windows should be reconciled before the mechanism is written up.
- The oracle's '1 of 15,653 lose history' does not count the 312 queued turns whose history went missing and was re-read early by the refetch, so next_use protection on its own is weaker than that figure suggests.
- As coded, next_use arrival protection flips to OVERDUE after 60 s in the queue. Moving it into a hint-free engine at 128-user queue lengths would need re-registration while the turn waits.

== setup: verdict claim_holds
Looking only at the setup, I found nothing besides the arm that differs between the six 128-user runs and could plausibly move mean TTFT by seconds. The 17.1 s gap between hint-free and oracle on the 8,175 shared turns (29.19 vs 12.06 s, means reproduced exactly) and the 25.2 s gap on the 10,066 turns they share both come from the arm. Server args, scripts, client inputs, request bodies, engine code, model and pools all match, apart from the arm's own flags and things that are inert (random_seed at temperature 0, client changes that only touch hint modes). Every arm starts with an empty SSD store, the L3 cleaner never fires in the first 2 h, and no other process does I/O on the SSD. The device saturates at the same ~2008 MiB/s in every run. At low concurrent write load, hint-free's big reads run at the same speed as the other runs (3.09 vs 3.06-3.18 ms per page), so its higher 3.63 ms median comes from its own 2.4-3x write traffic, not slower hardware. The only real setup difference is the GPU unit, whose measured speed matches within about ±2-3%; in a saturated closed loop of 128 sessions that is worth about 1-2 s at most, an order of magnitude below the gap.

== arm settings: verdict claim_partly_holds
Compared with the oracle and old-p50 runs, the hint-free run changes only two engine settings: the next-turn prefetcher is off and eviction is LRU instead of next_use. Both do nothing, or almost nothing beyond LRU, without hints. I found no other flag, env var, engine file, client request body or hardware difference that could carry the gap. The settings the arms share do not behave the same without hints, though. Every one of the hint-free run's 4,476 reads has no deadline ("now"), so the 512-page window and the prefetch budget never apply, and reads in flight hold a median 497K tokens of host room (39K in the oracle). The host-room refusals that follow are never retried, because poll interval 0 drops paced retries and this arm has no refetch to replace them: 535 reads revoked at dispatch and 632 turns whose lookup was declined at the 813,824-token cap. They cover about 83 % of the arm's 21.2M recomputed tokens, and the oracle had none. Pacing queued reads by queue position and retrying known hits need no hint information. So the 17 s gap is an upper bound on what hints buy, not a clean measure of it. For the two new just-in-time runs the claim fails: they use a different engine whose arrival hold paces reads of queued turns that have no plan, a mechanism that needs no hint.

- next_use eviction (horizon 300) vs LRU: what it does without hints
  evidence: It cannot run without the prefetcher (arg_groups/kv_cache_hook.py:393-399). The tiers are ENDED(0) < OVERDUE(1) < FAR(2) < UNKNOWN(3) < SOON(4) (mem_cache/next_use_eviction.py:25-29, 82-93). Without hints every committed tail is registered as ended, so the order becomes: registered tails by last_access_time, then unregistered nodes by last_access_time. Unregistered nodes are mostly split prefixes, which get a new id at split (unified_cache/unified_tree_core.py:1398-1404). The help text says the same: 'degrades to finished-first LRU on un-hinted traffic' (arg_groups/fields/memory.py:41-42).
