How each pair is read

Mean TTFT of the requests both designs sent in the first 110 minutes, paired by user and request, with a 95 % interval from resampling users.

What counts as a result

A difference outside the spread of two runs of one design. The current design, run again three days and a reboot later: +0.01 s [−0.09, +0.11].

Each setting runs the current design first, then the new arms, on the same GPU unit: the hold alone, the cache rules alone, and both. Every switch of the new engine is off by default. Expected values are for these users, seconds faster than the current design; the hold’s are upper bounds.

The last check is on the GPU. The current design and the unified one run on the same GPU unit, with the same users and the same requests, in four settings. The first is the setting of the earlier runs, 128 users and a 160 gigabyte host pool for two hours: the simulator expects the cache rules to be 0.3 seconds faster, all of it from the last 20 minutes when the cleaner starts, and the hold on the copy from host memory to be worth up to 3.1 seconds, which is an upper bound. The second is the same setting with the cleaner starting at minute 50 instead of 88, as on a store half the size; there the cleaner change acts for an hour; the simulator expects 0.8 seconds from the cache rules on the whole run, the page replay puts about three seconds at stake late in the run, and with the hold the bound is 3.8 seconds. The current design has run there: 11.56 seconds, 0.77 seconds slower than in the first setting on the same requests, with an interval from 0.61 to 0.92. The two runs differ only in when the cleaner starts, so this is the cleaner’s cost measured directly. The third has a tight host pool, 112 gigabytes, so that more history goes through the SSD; the simulator expects one second from the cache rules on these users and up to 4.1 seconds with the hold; this setting has no earlier run to anchor the simulator. The current design has run there too: 12.82 seconds, 2.3 seconds slower than with the larger pool, and with a very different shape: half of the requests get their first token within 0.3 seconds, while one in ten waits more than a minute. The fourth is at the knee, 64 users and 88 gigabytes for one hour, where the GPU pool fills only now and then; the simulator expects 0.2 seconds there; the current design measures 0.68 seconds. Each pair is read the same way as before: the mean TTFT of the requests both designs sent in the first 110 minutes, paired by user and request, with a 95 percent interval from resampling users. And a difference counts as a result only if it is outside the spread between two runs of the same design. The repeat of the current design in the first setting gives that spread: three days and one reboot after the earlier run, on another GPU unit, its mean TTFT is 10.97 against 10.96 seconds, and paired by request the difference is 0.01 seconds, with an interval from minus 0.09 to plus 0.11. So a tenth of a second is about what this comparison can resolve.
