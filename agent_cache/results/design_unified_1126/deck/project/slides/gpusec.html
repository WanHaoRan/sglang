The model · the queue, part 1

A second of GPU work delays every turn behind it

Users send their next request only after the reply and their pause, so the loop is closed:

R = N / X − Z

When the GPU is never idle it completes X = 1 / g requests a second, so

R = N · g − Z

One more GPU-second per request costs N seconds of response time each, and N − B seconds of TTFT: the B turns already past their first token lose no TTFT.

μ · the price of a GPU-second

Seconds of TTFT, summed over all turns, per second of GPU work added now.

Light load

μ is 1 to 3: the work delays its own turn, the few waiting, and those that arrive during it.

Saturated

μ = N − B, about 108 here; the runs measured 94.

One request in a hundred recomputing its history costs every request about a second.

R: mean time from a request to the end of its reply · N: users in session (128) · X: requests completed per second · Z: mean pause · g: GPU-seconds per request · B: turns running past their first token (about 20)

The queue enters the model through two weights. This is the first. In an agent workload a user sends the next request only after the reply has arrived and the pause, the tool call, is over. That makes the system a closed loop, and a closed loop obeys the response time law: the mean time from a request to the end of its reply, R, equals the number of users N divided by the throughput X, minus the mean pause Z. It holds for any policy. Now suppose the GPU is never idle. Then the throughput is one over g, the GPU-seconds a request takes, and the law reads R equals N times g minus Z. So if every request needs one more second of GPU work, every request’s response time grows by N seconds: with 128 users, 128 seconds. For the time to first token the factor is N minus B, where B is the number of turns already past their first token, about 20 here, because those lose nothing in TTFT. We call this factor mu, the price of a GPU-second: the seconds of TTFT, summed over all turns, that one second of added GPU work costs. At light load mu is between one and three: the work delays its own turn, the few turns waiting, and the turns that arrive while it runs. At saturation it is about 108, and the runs measured 94. The consequence for a cache policy is blunt. Recomputing a 25 thousand token history takes about a second of GPU time. If one request in a hundred does that, the average request needs a hundredth of a second more GPU time, and every request waits about one second longer.
