# kvsim: calibration (2026-11-26)

`kvsim` is a discrete-event simulator of the three-tier KV cache under the closed-loop replay of the FreeInference
trace. It was built to compare the current engine's policies with the rules of `../DESIGN.md` across load regimes and
seeds on CPU. This file says what was fitted and to what, what the simulator reproduces of campaigns 34, 32 and 28,
what it does not, and what it leaves out. Section 7 is generated by `calib_table.py` from the runs under
`calibration_runs/` (`rerun_calibration.sh` makes them, about 6 minutes).

## 1. Files and how to run

| file | what it is |
|---|---|
| `kvsim.py` | the simulator: client loop, GPU, host memory, SSD device, cleaner, outputs, command line |
| `kvsim_policy.py` | the policies: `hicache`, `jit_p50`, `jit_exact`, `ec_full`, `ec_exact`, `nohint`, and `unified` with the switches of DESIGN.md section 9 (one small method each) |
| `kvsim_trace.py` | the workload: the trace reduced to 64-token pages, the client's schedule, the hint table |
| `kvsim_compare.py` | arms x settings x seeds with at most 4 processes, and the paired comparison per user request |
| `calib_measured.py`, `calib_structure.py`, `calib_gpu_fit.py`, `calib_read_lags.py` | the measured side: anchors from the client records and the server logs (read-only) |
| `calib_table.py`, `rerun_calibration.sh` | section 7 and this file, from `calibration_notes.md` and the runs; the script that makes the runs |
| `trace_cache_freeinference_16w_ctx65536.pkl` | the 3,787 trees under MAX_CONTEXT 65,536, reduced (built once, 27 s) |
| `calibration_runs/calib`, `noise`, `triton`, `sens`, `notes`, `logs` | the runs behind sections 2 to 7 (requests.csv, series.csv, summary.json each) and the comparison printouts |
| `runs/`, `runs_final/` | runs of earlier versions of the code, superseded by `calibration_runs/`; safe to delete |

```
PY="CUDA_VISIBLE_DEVICES= nice -n 19 /home/wanhr/sglang/agent_cache/baselines/continuum/.venv/bin/python -I -B"
$PY kvsim_trace.py --build                       # once per trace and MAX_CONTEXT
$PY kvsim.py --arm ec_full --cap 128 --host-gb 160 --duration 7200 --seed 0 --out runs/x
$PY kvsim_compare.py --arms ec_full hicache "unified@F1+R4" "ec_full@mirror=off" \
    --set cap=128,host_gb=160 --set cap=44,host_gb=70 --seeds 0-4 --out runs/y
zsh rerun_calibration.sh                         # every run behind section 7, then calib_table.py
```

A 2-hour run takes 3 to 12 s of CPU. A run is deterministic for a seed; `--noise 0.005 --noise-seed k` sends each
request up to 5 ms late, to see how far the same users move between runs. In `kvsim_compare.py` an arm is
`NAME@option+option` (a switch, or a Config field as key=value) and a setting is `key=value,key=value`; a finished
run is not repeated unless `--force` is given.

Options of a run: `--arm`, `--cap`, `--rate`, `--host-gb`, `--duration`, `--seed`, `--gap-scale`, `--gap-cap`,
`--max-context`, `--backend fa3|triton`, `--fixes on|off` (the four write-path fixes of campaign 34), `--mirror
on|off`, `--hints none|program|dist|exact`, `--switches F1,...|all` (arm `unified`), `--gpu-tokens`, `--ssd-tokens`.
Outputs: per request (send, admission, TTFT, tokens from GPU / host / SSD / recomputed, stall, queue wait), per 10 s
(queue, ready queue, running, pool use, device busy share by reads and writes, host tokens by class, refusals, cleaner
passes, and mu, c, kappa, lambda, sigma as DESIGN.md section 6 defines them; lambda needs a hint and is 0 for
`hicache`), and the campaign records' statistics.

## 2. What it reproduces, in short

Seed 0 is the campaigns' own users (the simulated client matches the recorded one on all 17,095 requests of campaign
34's `ec_full`: prompt, output, wait, key, tree, arrival). The hint table matches too: of the 2,657 requests sent
before 1,200 s, 1,999 carry the identical hint (the same entry, sample count and p50, or no entry in both) and 573
the same entry with a sample count within 3; the rest differ by how concurrent sessions interleave.

- Campaign 34 (fixed engine, FA3). Mean TTFT of the five arms within 1 to 3 %: `hicache` 31.6 s against 31.9, the
  hinted arms 10.6 to 11.1 s against 10.7 to 11.5. HiCache is 2.9 times the hinted arms (measured 2.9). The four
  hinted arms are within 0.5 s of each other (measured 0.8 s). By half hour, all 20 cells within 10 %. Requests
  per minute within 1 % over the run and within 4 % at saturation. Tier shares within 3 %; history recomputed 0.40
  to 0.61 % against 0.39 to 0.53 % (hinted) and 29.1 % against 28.9 % (`hicache`). First cleaner pass 5,190 s
  against 5,252 to 5,301 s. Pinned memory of `jit_p50` 172 K median against 136 K. Reads staged before arrival
  1,216 / 103 / 1 against 1,208 / 99 / 1 (`jit_p50` / `jit_exact` / `ec_full`). The engine's learned price never
  moves (1,445 updates at 5e-5; measured 1,451). Who waits: 26 to 32 % of returning requests read from the SSD in
  minutes 90 to 110 and wait 47 to 70 s while the others wait 13 to 19 s; simulated 27 to 34 %, 46 to 67 s, 12 to
  17 s, arm by arm.
- Paired differences between arms (same users): `jit_p50` to `ec_full` -0.59 s [-1.02, -0.19] against -0.62
  [-1.02, -0.22]; `jit_p50` to `jit_exact` -0.65 s against -0.67 s; `hicache` to `ec_exact` -26.6 s against
  -27.0 s; `ec_full` to `jit_exact` a tie in both.
- Campaign 32 (no fixes). The loop of refused reads and SSD rewrites appears with no constant changed: mean TTFT
  31.8 / 15.1 / 13.5 / 13.6 / 13.6 s against 33.5 / 18.0 / 14.9 / 14.6 / 15.0 (`hicache`, `jit_p50`, `jit_exact`,
  `ec_full`, `ec_exact`; the median of six replicas of seed 0), pending writes peak at about 700 K tokens (measured
  523 to 675 K), 56 to 58 requests a minute in minutes 90 to 109 (measured 59 to 65). The loop starts at minute 81
  for `jit_p50` and 87 to 88 for the other three; measured 42 (67 by the stricter rule) and 79 to 84. With the fixes
  on no arm enters the loop in any seed.
- Campaign 28 (Triton backend, same users), with the Triton costs taken from the records and nothing fitted here:
  `hicache` 121.4 s against 115.7 s, the hinted arms 49.6 to 50.2 s against 48.3 to 49.8 s, requests per minute
  within 5 %.

Not reproduced, or only roughly:

- `ec_exact`'s 0.3 to 0.4 s lead over `ec_full` and `jit_exact` in campaign 34 (simulated: 0.03 s on average over
  the seeds, and the sign changes between seeds).
- Zero refused reads for `jit_p50` with the fixes on: the simulator refuses 46 of about 3,400 reads before the cut in
  seed 0 (3 to 46 across seeds); `ec_full`, `jit_exact` and `ec_exact` are at 0 in seed 0 (0 to 6 across seeds).
- The write hold switches on 51 to 80 times a run against 28 to 30, and pending writes are lower (p90 33 K against
  65 to 94 K); free host room is 12 K against 16 to 18 K.
- `jit_p50`'s loop onset in campaign 32 (minute 81 against 42 / 67), so its minutes 60-90 are too fast (22 s
  against 40 s) and its minutes 90-110 too slow (84 s against 69 s).
- The fixes gain less than measured: -0.2 s for `hicache` against -1.6 s, and -2.9 to -4.0 s for the hinted arms
  against -3.7 to -6.5 s (each run's own requests).
- History recomputed in campaign 28's hinted arms (0.2 to 0.4 % against 0.4 to 1.4 %; that engine still had the
  defect in the next-use rank of queued turns, which is not modelled).
- Not attempted: campaign 33 (TraceLab is a `lengths` trace; `kvsim_trace.py` reads `blocks` traces) and campaign 26
  (another trace, in the old turn format). The light-load anchor is campaign 34's first 30 minutes: mean TTFT 0.36
  to 0.40 s against 0.39 to 0.41 s, p50 0.08 to 0.09 s in both, and 70 to 77 % of prompt tokens from the GPU against
  68 to 76 %, in the same order across arms (`jit_p50` lowest, the exact-hint arms highest).

## 4. Taken from the engine's code or the run settings

KV pool 668,096 tokens; admission in arrival order among requests with no read under way, the first that does not
fit stops the pass (prompt beyond the GPU's part + output + 64 must fit free plus evictable tokens); prefill batches
of 8,192 tokens; max running 64. Host pool from HOST_GB (1,627,648 tokens at 160 GB). Lookup threshold 256 tokens;
`hicache`: paced miss retries every 8 scheduler steps, 8 re-issues a request, a re-lookup at admission when the match
shrank (every arm), LRU, no pins. Hinted arms: gate (3 lookups a turn), room retry (2 s, 8 times), refetch probe
0.5 s, hold margin 2 s, just-in-time margin 1 s, lead horizon 120 s, plan expiry, 512-page window, read budget half
the host pool, pins 0.3 of it and 600 s at most, write hold 50 K / 25 K, expected-cost start on the 64-point support,
price 5e-5 with the 'harm' rule, soft pins, next-use tiers (60 s grace, 300 s horizon), return-chance tiers (30 s),
the engine's read-time model (0.5 + 0.044 + 0.36 s plus the read thread's ms per page, EWMA 1/8). Cleaner at 90 %
down to 80 %, every 30 s, oldest write first; a skipped write (fix 1) touches the page. Client: the tree order and
the Poisson arrivals of `replay_programs.py` (`random.Random(f"{seed}:order")`, `f"{seed}:arrivals"`), the slot
semaphore, dependencies and waits, GAP and GAP_CAP, the deadline; hints as `gap_hints.OnlineGapTable` builds them
(per agent system, key then tool then `*`, 5 samples, `--hint-no-call`), or the exact next gap.

## 6. Not modelled, and what that limits

1. Pages. Memory and the SSD are tracked per node (a run of pages between two points where prompts diverge), not per
   page; nodes that the engine inserts in one piece (a read span, a recomputed history plus the new text) are evicted
   in one piece. A read never fails on a file the cleaner deleted between lookup and read (9 to 12 per arm in
   campaign 34), the cleaner works in an instant (11 to 12 s in the engine) and deletes whole nodes. Limits: the
   count of requests the cleaner hurts and anything about its order below the level of a node.
2. The node structure is fixed for a run (every divergence point of the run's users is known at the start), and the
   return-chance adoption of nodes by a session follows the engine's rule on that structure. Limits: small
   differences in which host pages are evictable; it is the likely source of the refusals `jit_p50` shows here and
   the engine did not.
3. Scheduler passes. The engine's prefetcher ticks every scheduler pass; the simulator every 0.25 s (probes every
   0.5 s as in the engine), and read dispatch also runs at every arrival, landing and write acknowledgement. The
   paced miss retries of `hicache` are placed 8 current decode steps apart. Limits: timing below about 0.3 s.
4. GPU. One prefill stream and one decode clock; no retraction of running requests, the output reservation is half
   the output, the copy from host to GPU is a cost per token, TPOT was not checked. GPU times 2 % shorter or longer
   move `ec_full`'s mean TTFT from 10.6 s to 9.3 or 11.8 s, and `hicache`'s from 31.6 s to 29.5 or 32.8 s
   (`calibration_runs/sens`); the two measurements of the decode step differ by 2.5 %. Limits: absolute TTFT is
   good to about 10 %; differences between arms on the same seed move much less (`hicache` minus `ec_full`: 25.4,
   26.6 and 27.0 s at the three speeds).
5. Host room that no logged lock explained at campaign 32's first refusals (0.25 to 0.5 M tokens) is not modelled
   (`unbacked_room_tokens` = 0), and no factor was fitted for it. The loop appears anyway, a few minutes late for
   three arms and 15 to 40 minutes late for `jit_p50`. Limits: onset minutes; whether a loop appears is reproduced.
6. Write path. Writes are one FIFO of nodes at the device's rate: merged writes (fix 2) have no effect of their own
   here, a write has no fixed cost, the GPU-to-host copy takes no time, and a write fails only if `write_fail_p` is
   set (so R3 does nothing by default). Limits: which of the four fixes does the work: fix 1 and fix 3 can be
   separated here, fix 2 cannot.
7. Defects of older engine copies (the next-use rank of queued turns before 2026-11-22) and outside requests are
   not modelled; campaign 28 is compared as if it had run the current policies with the fixes off.
8. Run-to-run noise of the real system is not modelled beyond `--noise`; the real spread at saturation was never
   measured.
9. Other traces: `lengths` traces (TraceLab) are not read; campaign 26's setting can be run (`--cap 44 --host-gb 70
   --backend triton --gap-scale 10`) but only on the FreeInference trace, so its numbers are not anchors.
10. The Triton cost set was checked on campaign 28 only.
11. The arm `nohint` (the next request's id only: gate, hold, pins, queued turns last, LRU otherwise) has no
    anchor: no such arm ran on FA3.

The unified arm's switches, as implemented from draft v1 (each is one method in `kvsim_policy.py`; base = `ec_full`):

| switch | implementation |
|---|---|
| F1 | the hold releases a queued turn's read to land at the q-quantile of the admission time, q = lambda L / (c + lambda L); the admission time's spread is the measured ratio of waits to their estimates at arrival (last 256 admissions); replaces the 2 s margin |
| F2 | `read_start` weighs stall by the measured c |
| F3 | the read time used before arrival counts the parked reads and the rest of a write hold |
| F4 | at a hit, recompute instead of reading when mu x (GPU seconds for L tokens at their position) < c (r - W)+ + kappa L / beta + lambda L r |
| F5 | a lookup that finds nothing is not charged to the turn's 3 lookups (`hicache`: not to its 8 re-issues) |
| R1 | the last turn of a session the agent declared ended is not written; its own SSD pages go first at the cleaner |
| R2 | the write queue serves the pending page the eviction order would take first |
| R3 | a failed write is queued again instead of counting as clean (needs `write_fail_p` > 0 to matter) |
| R4 | pages that memory serves are touched on the SSD (heads stay younger than tails); ended sessions' pages go first |
| R5 | eviction by the index of DESIGN.md 4.1, nu = (K / L) x sup F / tau on a grid of horizons, with K = mu x gamma for a page with no SSD copy; ended sessions first, queued turns last and by distance from admission |
| P1 | a read short of room first takes idle pages, then lets staged reads yield, then takes queued turns' pages only where the turn can read them again before admission (farthest first); otherwise it waits (refused after 60 s as a safety valve) |
| P2 | no 50 K / 25 K threshold: timed reads wait for writes only when a read found no room while writes were pending, or the evictable reserve is under the next due read |
| PR1 | lambda is read off the eviction frontier (the highest index given up in the last 30 s) instead of the engine's learned price; FA3's recompute cost replaces Triton's 1.1e-4 s a token in the harm charge |

Logged for the design, not evaluated here (seed 0, one run each, `calibration_runs/notes`):

- The index contains lambda through K_read (the term lambda L r), so a price read off the eviction frontier feeds
  itself; it grows without bound once (read time) x (return hazard of the marginal holder) reaches 1. The simulator
  caps lambda at 1e-3 (the engine's ceiling); with PR1 on it sits at that cap from minute 60.
- In F4's K_read the rent lambda L r uses r with the device's line in it, while a parked read holds no host memory.
  With a long line the rule prefers recompute at saturation (3,403 recomputes by choice, mean TTFT 13.3 s against
  10.6 s).
- With F3 the read time before arrival exceeds the queue wait, and the expected-cost rule stages 905 reads where it
  staged 1 (pins 45 K at the median, +0.31 s paired [+0.05, +0.58]).
- Measured prices at saturation (minutes 60 to 110, `ec_full`): c is 0.00, mu about 30 (1 + ready turns waiting, not
  128), kappa 0, lambda about 1e-4 by the frontier.
- Mirror off (`--mirror off`: a clean page the GPU holds gives up its host copy, and is copied back when the GPU
  gives it up) frees 0.5 M tokens of host room and cuts the SSD share of prompt tokens from 0.140 to 0.078. With the
  copy made inline at the measured 2.8 us a token it costs 10 % of throughput (16.7 s against 10.6 s); with an
  asynchronous copy (`--d2h-s-per-token 0`) mean TTFT is 10.4 s and p99 32.5 s against 54.1 s.
