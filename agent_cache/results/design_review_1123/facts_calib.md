# calib

## summary
Nothing that exists today can serve as the simulator, but several pieces can be reused. The only closed-loop discrete-event model, frozen/oracle_scripts_staging/c20_dist/qps_sim.py, admits requests at a fixed 2.4 turns/s, so its queue wait cannot respond to recompute. room_model.py (event-driven, calibrated room of 90K tokens) and evict_replay.py replay one recorded run's timeline, so the queue wait and eviction are held fixed. mock_engine.py is a wall-clock stand-in for client tests, and toy_floor.py is a synthetic floor with no queue. All of them were calibrated on Triton and the older agentic trace, and all read the old 'turn' client format. adapt_runs.py converts the campaign 32/34 runs to that format but drops the hints. None models the SSD write path, host memory locked by pending writes, refused reads, the SSD cleaner, or page-level shared prefixes. Calibration for campaigns 32/34 (the brief's model is wrong): the runs served Qwen3-30B-A3B-Instruct-2507 with bf16 KV, not Qwen3-32B-FP8, so KV is 98,304 B/token and 6 MiB per 64-token page. The GPU pool is 668,096 tokens and binds at 19-23 running requests, well below max_running 64. The host pool is 1,627,648 tokens, of which the GPU mirror takes about 0.65 M. FA3 prefill costs 0.0365-0.0374 ms/token, plus 27-35 ms per batch, plus about 0.25 µs per token per 1K of prefix; all-in that is 0.047-0.062 ms/token. A decode step takes 3.3-3.5 ms + 0.47-0.68 ms per running request + 0.010-0.016 ms per 1K context tokens. There is one read thread (2.4-3.7 ms/page, 4.6-4.9 in campaign 32's loop) and one write thread (3-12 ms/page, slower as reads rise). Both share one SSD that tops out at 2.10-2.11 GB/s for reads and writes combined. The cleaner deletes about 235 GiB, oldest mtime first, whenever the volume passes 90 %, down to 80 %. Workload: 729 Poisson users arrive (0.1/s, at most 128 in session). The client is closed-loop: each request waits for the previous one to complete plus its recorded wait, capped at 1,200 s. 88 % of requests follow tool waits (p50 1.0 s) and 7.6 % follow user waits (p50 64 s). Prompts average 25.5K tokens with 1.1K new; outputs average 280 tokens; 47 % of requests are SWE-bench. Validation targets per arm: requests per minute, TTFT mean/p50/p90, tier shares, history recomputed, and the queue wait, which is about 97-98 % of TTFT. Campaign 32's loop onset minutes are 67/71/79/80/84 for the hinted arms and 39-42 for hicache's storm; campaign 34 shows no loop at all; campaign 28 (Triton) is a second regime where the arms tie.

## findings
- [verified] **existing models: mock_engine.py**: A wall-clock aiohttp stand-in for the server, not a discrete-event simulator. It runs a three-tier page-level LRU prefix cache (chained page hashes, write-through), admits a request when its pages fit, prefills one request at a time with T = 0.092 + n/1.19e6 + 3.21e-9(n^2 - c^2) s (the Triton 30B-A3B fit) plus host/storage loads at 400K/21.5K tok/s, and decodes each request at a fixed 12 ms/token with no batch contention. It has no SSD queue, no write path and no hints. Its own docstring says nothing measured on it belongs in a paper. Reusable for testing replay_programs.py and for TieredCache's hashing.

- [verified] **existing models: room_model.py**: Event-driven (heapq), open-loop replay of one recorded run's SSD reads. It keeps the run's arrivals, queue waits, pages to read and re-reads, and varies only read start and revocation. One FIFO read thread serves reads at the run's median ms/page per 10-minute bin plus 10 ms. Timed reads dispatch below a 512-page window; a revoked read retries after 1 s, up to 3 lookups, then recomputes at a flat 9,000 tok/s. Policies: asrun, arrival, oracle, fixed quantile, expected cost (rule 1) on split/histogram/sample forms, soft pins. One free parameter, the room, calibrated at 90K tokens: counts within about ±25 %. No TTFT, no write path. Inputs: campaign 23 (Triton, 44 users, 70 GB, x10 gaps).

- [verified] **existing models: qps_sim.py (the one closed-loop DES)**: Closed-loop discrete-event model (heapq) from campaign 20. Users arrive, at most C are in session, and the rest wait in a FIFO list. The GPU admits FIFO at a fixed LIMIT of 2.4 turns/s, and the SSD serves reads FIFO at 3.3 ms per 64-token page. Each session is one unit. Eviction follows engine-like tiers (ended, overdue, far, soon); reads are staged within 120 s of predicted admission under a 30 % pin budget, and plans expire at max(60 s, gap). Its docstring lists what is missing: recompute (so the GPU rate does not depend on U), re-evicted reads, retries and storms, the deadline read order, shared prefixes and partial eviction. It also lacks the write path and refusals. Reusable as an event-loop skeleton with user-cap admission.

## discrepancies
- The brief names the served model as Qwen/Qwen3-32B-FP8. Campaigns 28, 32 and 34 actually served Qwen3-30B-A3B-Instruct-2507 with bf16 KV (98,304 B/token), context 262,144, on FA3. start_server.sh's defaults (MODEL Qwen3-32B-FP8 at :43, KV fp8_e5m2 at :45, Triton at :88) are overridden by run_campaigns.sh:75 (MODEL, CTX, KV_DTYPE=auto, L3_CLEANER_PCT=90,80) and the queue lines' --attention-backend fa3. With the 32B FP8 model b would be 131,072 B/token (RUNBOOK.md:118), and every b/β number would shift by a third.
- Paper design.tex:99 assumes storage holds every prefix cache. In the runs the SSD is a cache too: the cleaner deletes about 235 GiB, oldest mtime first, from 90 % down to 80 % (nixl_cleaner.py:168-212). In campaign 34, history recomputed rose from 3-4 K to up to 290 K tokens a minute after the first pass at minute 87-88 (campaign34/DECISIONS.md:103-105).
- Paper design.tex:107-108 uses r_i = bL_i/β with one β shared by reads and writes. The engine's own read-time model is 0.86 s of fixed lags plus a measured ms/page × (own + backlog pages) (next_turn_estimators.py:119-145). The device is not split evenly: at saturation, campaign 34 ran 1.72 GB/s of reads against 0.39 GB/s of writes, with writes slowing from 3-4 to 9-12 ms/page, while campaign 32's loop ran 1.0/1.0 (iostat_vdc.log of both campaigns). r depends on the read backlog and the write load, not on L alone.
- Paper design.tex:118-131 says attention dominates prefill, puts the read/recompute crossover at b/(2ρβ), and states that agentic contexts easily pass it. That holds on Triton (ρ = 3.21e-9 s/token², crossover about 7.1K tokens; cpu_calib_c44/FINDINGS.md:156-158). On FA3 the per-token cost is mostly linear: 0.0374 ms at prefix 0 against 0.0436 ms at 25K (mechanisms.tgz cross_backend_verify/cost.out). ρ_FA3 is about 1.2-3.6e-10, so the crossover lands at about 33-37K tokens, above the replayed mean history of 24.9K (inferred). The deck's constants (b/β ≈ 47 µs, 2ρx ≈ 6.4 ns·x; deck_formulas.py:58-59) are Triton's.
- Design note §1-2: 'HiCache recomputed 36 % of prompt tokens, the rules arm 12 %'. Those are compare_arms' 1 - cached/prompt (compare_arms.py:99; program_summary.py:98), which also counts first-request prompts and new tokens (a floor of about 6 %). History recomputed is (1 - recomputed) × (1/delivered - 1): 29 % for hicache and 6 % for ec_full in campaign 32, and about 0.5 % in campaign 34 (arithmetic on campaign32/compare_arms.out and campaign34/compare_arms.out).
- Design note §2: 'one read thread, 83-96 % busy on FreeInference'. That is campaign 28 on Triton (mechanisms_findings.txt:182). On FA3, campaign 34's read thread averaged 48-80 % busy over minutes 30-110 and reached 100 % only from about minute 70-90 (campaign34/checks/read_thread.out).
- Design note §2 prices recompute at 0.042-0.044 ms per token under load. That fits whole-history recomputes in 8K chunks. Small prefills also pay a 27-35 ms per-batch term, and campaign 34's all-in prefill came to 0.062 ms/token (campaign34/checks/decode_scale.out, last line). A per-token-only W model will undercount the cost of many small prefills.
- The brief lists max_running 64 as a calibration constant. In every saturated FA3 run the 668,096-token KV pool binds first (19-23 running at 0.97-0.98 pool use; campaign34/checks/by_minute_*.out, campaign32/DECISIONS.md:105). A simulator that admits up to 64 will overstate throughput.
- OPEN_ITEMS.md §1 places MAX_REFETCHES at next_turn_prefetch.py:108. The current file, identical to the frozen engine_fa3fix_20261122 copy, has it at :110, as the design note says. Minor line drift.
- Every existing CPU model is calibrated to other settings, so its constants do not transfer to FreeInference on FA3. room_model RHO 9,000 tok/s and ROOM 90K (campaign 23, Triton, 44 users, x10); qps_sim LIMIT 2.4 turns/s and READ_S 3.3 ms/page (campaigns 18-20); evict_replay M 982K (campaign 23/25); mock_engine prefill (Triton probe).

## open questions
- What tolerance should a simulator be held to? The saturated part of campaigns 32/34 was never repeated, and campaign 34's arms differ by only 0.6-0.7 s. Seeds in a simulator can estimate the spread from arrival draws, but only a GPU repeat measures the engine's.
- FA3 prefill above 30K tokens: only one cold request at 53K was measured. Is the loaded regression (0.0374 ms/token + 34.6 ms/batch + 0.25 µs per token per K prefix) good enough, or is an FA3 length sweep (GPU time, after the running campaign) needed before the paper states ρ?
- How should the shared SSD be modeled? At saturation, reads got about 80 % of 2.1 GB/s in campaign 34 but about 50 % in campaign 32. Is that the device, transfer sizes (512-page read windows against merged 128-page writes), or the one-read-thread, one-write-thread structure? The write-path policies the user wants to compare depend on it.
- What held host memory at campaign 32's first refusals? Logged locks covered only 0.2-0.5 M of the 0.98 M room beyond the mirror (campaign32/DECISIONS.md:182-185); the census exists only from campaign 34. A simulator's room accounting may not reproduce the onset minutes without knowing this (radix ancestors of locked nodes, anchor locks of parked lookups).
- How should the workload be extracted? load_model.py's route (replay_programs.load_trees over the 662 MB trace, all 3,787 kept trees in memory) gives the exact 729 users with block-level prefixes but should run once in the container off-peak. The client logs hold only what each arm sent in 2 h, which is arm-dependent.
- Should the simulator model block-level prefix sharing (17 % of prompt tokens are held by earlier sessions; first requests find 24 % held) and context rewrites (2 % of returning requests add more than 8K new tokens)? Or are session-level units, as in qps_sim, enough to rank fetch and eviction policies?
- Which engine behaviours should be replicated rather than idealized: wait_complete admission passing over requests still reading; the MAX_REFETCHES allowance and defect 1's empty lookups (0-17 capped per window in campaign 34); hicache's 8 attempts at 8 s; the write hold; room retry? Each changed results in campaigns 32/34.
- SGLang admits a request only if its prompt plus reserved output fits the pool. The simulator needs an admission rule that reproduces 19-23 running at 0.97 pool use; the reservation ratio is not in the records.
